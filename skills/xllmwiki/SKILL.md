# xllmwiki

위키는 나중에 읽는 것이 원본을 다시 읽는 것보다 나을 때만 만들 가치가 있다.
아래 모든 규칙은 이 제약 하나에서 나온다. 페이지가 원자적인 이유는 선택적으로
로드해야 하기 때문이고, 주장에 인용을 붙이는 이유는 원본 없이도 신뢰할 수 있어야
하기 때문이고, 인덱스를 최신으로 유지하는 이유는 그러지 않으면 페이지를 아예 찾을
수 없기 때문이다.

RAG 저장소가 아니다. 임베딩도, 벡터 DB도, 데몬도 없다 — `grep`으로 찾히고 사람이
읽고 고칠 수 있는 순수 마크다운이다.

## 레이아웃

**단일 도메인** — 주제가 하나일 때. 대부분 여기서 시작한다.

```
.xllmwiki               # 마커: 스크립트가 이 파일을 찾아 위키 위치를 안다
purpose.md              # 이 위키가 무엇을 위한 것인가 — 모든 작업이 참조
wiki/
  index.md              # 지도: 모든 페이지를 한 줄씩
  log.md                # append-only: 무엇을 언제 흡수했는지
  SCHEMA.md             # 이 위키의 지역 규약 (태그 목록, 고유 규칙)
  concept/<slug>.md     # 페이지는 타입별 디렉터리에
  entity/<slug>.md
  source/<slug>.md
  synthesis/<slug>.md
  graph/                # (선택) 컴파일된 질의 인덱스, 언제든 재생성 가능
raw/<slug>.md           # 원본 텍스트 그대로, 절대 편집하지 않음
```

**멀티 도메인** — 주제가 갈라질 때. 도메인마다 독립된 `wiki`+`raw`를 가지므로 하나를
통째로 옮기거나 지울 수 있다.

```
.xllmwiki               # {"root": "_WIKI"}
_WIKI/
  index.md              # 도메인 목록만 (페이지 목록이 아니다)
  SCHEMA.md             # 모든 도메인에 적용되는 공통 규약
  domainA/
    raw/
    wiki/{index.md, log.md, SCHEMA.md, concept/, entity/, source/, synthesis/, graph/}
  domainB/
    ...
```

루트에 `log.md`는 없다 — 흡수는 항상 특정 도메인에서 일어나므로 루트가 기록할 내용이
없다. 루트 `index.md`는 도메인 목록이고, 페이지 목록은 각 도메인의 `index.md`가
가진다. 두 파일이 같은 것을 담지 않으므로 동기가 깨질 여지가 없다.

## 페이지는 타입별 디렉터리에

`concept` · `entity` · `source` · `synthesis` 각각 디렉터리 하나. 이유는 사람이다 —
옵시디언 vault로 열었을 때 한 폴더에 수백 개가 늘어지면 탐색이 불가능하고, 접히는
폴더 넷은 가능하다. 위키는 필연적으로 커지므로 처음부터 나눈다.

**frontmatter의 `type:`이 정본이고 디렉터리는 그것의 거울이다.** 둘이 어긋나면 컴파일이
`type mismatch`로 보고한다. 타입이 바뀌면 `type:`을 고치고 파일을 해당 디렉터리로
옮긴다 — 복사하면 같은 slug가 두 곳에 생기고, 컴파일이 `duplicate slug`로 잡는다.

`[[링크]]`는 타입과 무관하게 slug만 쓴다. 경로를 쓰지 않으므로 타입이 바뀌어도 링크는
그대로 유효하다.

`raw/`가 존재하는 이유는 인터넷을 다시 긁지 않고도 주장을 재확인할 수 있어야 하기
때문이다. 페이지는 이곳을 인용하며, 실질적으로 append-only다.

**위키가 없으면 먼저 만든다** — `references/init.md`를 따른다. 경로는 마커가 결정하므로
CWD에 의존하지 않는다.

작업 시작 시 `wiki/SCHEMA.md`가 있으면 읽는다 (멀티 도메인이면 루트 것도). 태그 목록과
이 위키의 고유 규칙이 거기 있다.

## 스크립트 경로

스크립트는 이 스킬 디렉터리의 `scripts/` 아래에 있다. 플러그인은 설치 위치가 다르므로
**절대 경로로 실행한다.** 이 SKILL.md 파일이 있는 디렉터리를 기준으로 삼는다.

```bash
# 이 SKILL.md가 <skill>/SKILL.md라면 스크립트는 <skill>/scripts/
python3 "<skill>/scripts/wiki_init.py"
python3 "<skill>/scripts/wiki_graph.py"
python3 "<skill>/scripts/wiki_query.py" map
```

아래 문서들이 `scripts/…`로 짧게 쓰는 것은 모두 이 절대 경로를 뜻한다. `python3`가
없는 환경이면 `python`을 쓴다.

## purpose.md

위키의 목적을 담은 파일. 목표, 다루는 범위, 답하려는 핵심 질문을 적는다.

```markdown
# 목적

LLM 추론 최적화를 실무에 적용할 수 있을 만큼 이해하기.

## 범위

포함: 추론 지연·메모리, 서빙 아키텍처, 양자화.
제외: 학습 기법, 모델 아키텍처 연구 그 자체.

## 핵심 질문

- 컨텍스트 길이가 길어질 때 실제 병목은 어디인가
- 양자화가 품질을 얼마나 희생하는가
```

**모든 작업의 시작점에서 읽는다.** 흡수에서 무엇을 생략할지, 질의에서 어떤 공백을
보고할지가 여기서 결정된다. 이 파일이 없으면 판정 기준이 매번 즉흥적이 되고, 위키는
목적 없이 커진다.

없으면 만들 것을 제안한다 — 사용자에게 목표와 범위를 물어 세 문단으로 쓴다. 사용자가
건너뛰겠다면 진행하되, 생략 판정을 보수적으로(의심스러우면 남긴다) 한다.

목적은 시간이 지나며 바뀐다. 흡수 중 범위 밖 주제가 반복해서 나타나면 `purpose.md`
갱신을 제안한다 — 조용히 범위를 넓히지 말 것.

## 워크플로

당면 작업에 해당하는 레퍼런스 파일을 로드한다. 두 개 이상 로드하지 않는다.

| 작업 | 레퍼런스 |
|------|----------|
| 위키 생성 · 도메인 추가 | `references/init.md` |
| 소스 추가 | `references/ingest.md` |
| 위키 기반 응답 | `references/query.md` |
| 상태 점검 · 복구 | `references/lint.md` |
| 소스 · 페이지 삭제 | `references/delete.md` |
| 그래프 컴파일 · 질의 | `references/graph.md` |

페이지 구조와 frontmatter는 `references/page-format.md`에 있다. 한 세션에서 페이지를
처음 작성하거나 편집할 때 읽는다.

## 모든 워크플로에 공통으로 적용되는 규칙

**한 페이지에 한 개념.** 부모·자식 관계가 아닌 `#` 제목이 두 개 필요하다면 두 개의
페이지다. 긴 페이지는 나중에 읽는 사람이 건너뛰고, 그러면 짐이 된다.

**페이지에는 타입이 있다.** frontmatter의 `type:` 필드로 구분한다.

| type | 답하는 질문 | 예 |
|------|-------------|-----|
| `concept` | "X란 무엇인가" | KV 캐시, 양자화 |
| `entity` | "누가·어디가 무엇을 했나" | vLLM, Anthropic |
| `source` | "이 소스가 무엇을 주장했나" | 특정 논문의 요약 |
| `synthesis` | "여러 소스를 합치면 무엇이 보이나" | 양자화 기법 비교 |

**소스마다 `source` 페이지 하나를 만든다.** "이 논문이 뭐라고 했나"는 "KV 캐시란
무엇인가"와 다른 질문이고, `source` 페이지 없이는 답할 곳이 없다. 소스의 주장·방법·
한계를 담고, 거기서 뽑아낸 `concept`·`entity` 페이지로 링크한다.

**같은 소스를 인용하는 페이지들은 서로 관련이 있다.** `sources[]`가 겹치는 것은 직접
링크보다 강한 신호다 — 링크는 누군가 걸어야 생기지만 소스 겹침은 저절로 생긴다.
검색할 때 링크만 따라가지 말고 `sources[]`로도 찾는다.

**자명하지 않은 모든 주장은 인용한다.** 형식은 `raw/<slug>.md` 또는 URL로 연결되는
`[^src]` 각주다. 인용할 수 없는 주장은 배경지식(괜찮다, 인용하지 말 것)이거나
추론이다 — 추론은 `(추론)`으로 표시해서 나중 세션이 당신의 추측을 사실로 승격하지
않게 한다.

**추가보다 갱신.** 기존 페이지와 모순되는 소스는 그 페이지를 편집하고 불일치를
기록한다. 서로 반대되는 주장을 하는 페이지 두 개를 남기지 말 것 — 그렇게 위키는
없는 것보다 나빠진다.

**인덱스는 선택이 아니다.** `index.md`에 없는 페이지는 보이지 않는 페이지다.
페이지를 만드는 그 작업에서 함께 갱신한다, 절대 "나중에"가 아니다.

**낯선 사람을 위해 쓴다.** 독자는 이 대화의 문맥을 하나도 모르는 미래의 세션이다.
약어를 풀어 쓰고, 소스를 명시하고, 무엇이 흥미로운지 말하기 전에 그것이 무엇인지
말한다.

## 규모 확장

약 50페이지 이하에서는 `index.md`를 하나의 평면 목록으로 두면 충분하고 `grep`으로
뭐든 찾을 수 있다. 그 이상이면 인덱스를 타입·태그별로 샤딩하고 페이지 간 `see-also`
링크를 추가한다 — 인덱스가 카탈로그가 아니라 라우터가 된다. 페이지 디렉터리는 이미
타입별로 나뉘어 있으므로 추가 분할은 필요 없다. 인덱스 샤딩을 미리 만들지 말 것.
12페이지 위키에 샤딩된 인덱스는 그냥 마찰이다.

한 타입 디렉터리가 수백 개로 커지면 주제가 갈라졌다는 신호다 — 디렉터리를 더 쪼개기
전에 도메인 분리를 검토한다 (`references/init.md`).

그래프 인덱스(`references/graph.md`)는 별개의 선택지다. `grep`이 답하기 힘든 질문 —
"무엇이 무엇에 의존하나", "이 둘이 어떻게 이어지나" — 이 반복되거나, 페이지가 많아
읽는 비용이 부담될 때 컴파일한다. 200페이지를 넘으면 그래프도 자동으로 샤딩된다.
