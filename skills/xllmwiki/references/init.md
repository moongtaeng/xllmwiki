# 초기화 (Init)

위키를 만드는 작업. 디렉터리 몇 개와 마커 파일 하나가 전부다.

```bash
python3 "<skill>/scripts/wiki_init.py"                    # 단일 위키
python3 "<skill>/scripts/wiki_init.py" --domain infra     # 멀티 도메인, 첫 도메인
python3 "<skill>/scripts/wiki_init.py" --domain poker     # 도메인 추가
```

이미 있으면 아무것도 바꾸지 않고 현재 구성을 보고한다. 멱등하다.

## 두 가지 레이아웃

**단일** — 주제가 하나인 위키. 대부분 여기서 시작한다.

```
.xllmwiki                # 마커
wiki/
  index.md  log.md  SCHEMA.md
  concept/  entity/  source/  synthesis/    # 페이지는 타입별로
raw/                     # 원본
```

**멀티 도메인** — 서로 다른 주제를 한 저장소에서. 도메인마다 독립된 `wiki`+`raw`를
가지므로 하나를 통째로 옮기거나 지울 수 있다.

```
.xllmwiki                # {"root": "_WIKI"}
_WIKI/
  index.md               # 도메인 목록 (페이지 목록이 아니다)
  SCHEMA.md              # 모든 도메인 공통 규약
  infra/
    wiki/{index.md, log.md, SCHEMA.md, concept/, entity/, source/, synthesis/}
    raw/
  poker/
    ...
```

루트에 `log.md`는 없다 — 흡수는 항상 도메인 안에서 일어나므로 루트가 기록할 것이 없다.
루트 `index.md`는 도메인 목록만 담고, 페이지 목록은 각 도메인이 가진다. 두 파일의
역할이 겹치지 않으므로 동기가 깨질 여지가 없다. 루트 `index.md`는 도메인을 추가할 때
스크립트가 다시 쓴다.

`purpose.md`는 도메인마다 하나다 (`_WIKI/<domain>/purpose.md`). 도메인이 다르면 목적도
다르므로 공통으로 두지 않는다.

## 인덱스는 모든 관리 문서를 가리킨다

`index.md`가 가리키지 않는 문서는 옵시디언 그래프에서 고립되고, 나중에 있는 줄도
모르게 된다. init이 아래 링크를 넣어두므로 지우지 말 것.

- 도메인 `index.md` → `[[SCHEMA]]`, `[[log]]`, `../purpose.md`
- 루트 `index.md` → `[[SCHEMA]]`, 그리고 **모든 도메인의 `index.md`**

도메인을 추가하면 루트 `index.md`에 그 링크가 반드시 들어가야 한다. 없으면 그 도메인은
위키 전체에서 보이지 않는다. `wiki_init.py --domain`이 루트 인덱스를 다시 쓰므로
스크립트로 추가하면 자동으로 처리된다 — 손으로 디렉터리를 만들면 빠진다.

`SCHEMA.md`·`log.md`·`index.md`는 도메인마다 하나씩 있으므로 vault 안에 같은 이름이
여럿 존재한다. 옵시디언은 `[[SCHEMA]]`를 같은 폴더의 것으로 해석하므로 실사용에는
문제가 없다. 다만 도메인 간 링크를 쓸 때는 `[[alpha/wiki/SCHEMA]]`처럼 경로를 명시해야
의도한 파일에 걸린다.

도메인 사이 링크는 페이지 slug로 걸면 된다 — 페이지 slug는 위키 전체에서 고유하고,
컴파일이 `cross-domain links`로 보고한다.

미리 멀티로 만들지 말 것. 주제가 실제로 갈라질 때 도메인을 추가한다. 단일 위키를
멀티로 바꾸려면 `wiki/`와 `raw/`를 컨테이너 아래의 도메인 디렉터리로 옮기고 마커에
`{"root": "_WIKI"}`를 적는다.

## 페이지 디렉터리

`concept` · `entity` · `source` · `synthesis` 각각 하나. 이유는 사람이다 — 옵시디언
vault로 열었을 때 한 폴더에 수백 개가 늘어지면 탐색이 불가능하다. 위키는 필연적으로
커지므로 처음부터 나눈다.

`type:` frontmatter가 정본이고 디렉터리는 거울이다. 어긋나면 컴파일이 `type mismatch`로
보고한다. 타입이 바뀌면 `type:`을 고치고 파일을 옮긴다 — 복사하면 `duplicate slug`로
잡힌다.

`[[링크]]`는 slug만 쓰므로 타입이 바뀌어도 링크는 유효하다. 스크립트가 네 디렉터리를
훑어 slug를 해석한다.

## 마커 (`.xllmwiki`)

**존재 이유는 하나다** — 스크립트가 상위 디렉터리로 올라가며 이 파일을 찾는다. 덕분에
프로젝트 어느 하위 디렉터리에서 실행해도 위키를 찾는다. 마커가 없으면 `wiki/`가 있는
정확한 디렉터리에서만 동작한다.

내용은 기본값과 다를 때만 적는다.

```json
{"root": "_wikiroot", "wiki": "wiki", "raw": "raw"}
```

| 키 | 뜻 | 기본값 |
|---|---|---|
| `root` | 도메인들을 담는 컨테이너. 없으면 단일 레이아웃 | 없음 |
| `wiki` | 페이지 디렉터리 이름 | `wiki` |
| `raw` | 원본 디렉터리 이름 | `raw` |

기본값 그대로면 사람이 읽을 주석만 남는다. 파싱 실패해도 마커로는 유효하다 — 위키
위치를 표시하는 것이 주 역할이므로, 사람이 메모를 적어 넣어도 깨지지 않는다.

**경로 설정은 이 파일에만 있다.** `SCHEMA.md`에 중복해 적지 말 것 — 두 곳이 어긋나면
무엇이 맞는지 알 수 없게 된다.

## SCHEMA.md

위키별 지역 규약. 태그 목록, 이 위키에만 적용되는 규칙. 스킬이 기본값을 제공하므로
여기엔 **이 위키에 고유한 것만** 적는다.

```markdown
## 태그 목록
- inference — 실행 시 비용, 지연, 메모리

## 지역 규칙
- 한글 페이지는 제목도 한글로 둔다. slug를 번역하지 않는다.
- 벤치마크 수치는 측정 하드웨어를 반드시 함께 적는다.
```

짧게 유지한다. 여기 한 줄은 페이지를 쓸 때마다 읽어야 하는 한 줄이다.

`CLAUDE.md`가 있으면 링크해두면 세션 시작 시 문맥에 들어온다. 링크가 없어도 스킬이
위키를 찾을 때 함께 읽으므로 필수는 아니다.

## purpose.md는 자동 생성하지 않는다

목표·범위·핵심 질문은 사용자에게 물어서 쓴다. 템플릿을 남기면 채워지지 않은 채로
남아 판정 기준 역할을 못 한다. `xllmwiki` 스킬의 purpose.md 절을 따른다.

## 도메인 간 경계

도메인 간 `[[링크]]`와 타입 관계는 **허용된다**. 지식은 원래 폴더 경계를 넘는다.

컴파일은 이를 오류가 아니라 `cross-domain links`로 보고한다. 전체 현황은:

```bash
python3 "<skill>/scripts/wiki_query.py" domains
```

질의는 기본적으로 한 도메인만 본다 — 현재 디렉터리가 속한 도메인, 또는 `--domain`으로
지정한 도메인. 컴파일은 `--all`로 전체를 돌린다.
