# 흡수 (Ingest)

소스를 페이지로 바꾸는 작업. 산출물은 소스의 요약이 아니다 — 위키에 없었고 이 소스가
채워주는 것, 그것만이 산출물이다.

읽으면서 바로 쓰지 않는다. **먼저 소스 전체를 분석해 무엇을 쓸지 결정하고, 그다음에
쓴다.** 이 분리가 중복 페이지를 막는다. 읽으면서 쓰면 3페이지째에 만든 페이지를
7페이지째에 또 만든다.

## 0. 위키와 목적을 확인한다

위키가 없으면 먼저 만든다 (`references/init.md`). 멀티 도메인이면 어느 도메인에
넣을지 정한다 — 애매하면 사용자에게 묻는다.

`purpose.md`를 읽는다. 무엇을 생략할지가 여기서 결정된다. 없으면 만들 것을 제안한다
(`xllmwiki` 스킬의 purpose.md 절 참조). `wiki/SCHEMA.md`가 있으면 태그 목록과 지역
규칙을 함께 읽는다.

## 1. 소스를 보존한다

다른 무엇보다 먼저 원문 텍스트를 `raw/<slug>.md`에 저장한다. 저장하지 않은 URL
fetch는 나중에 재확인할 수 없는 주장이다.

이미 디스크에 있는 로컬 파일이라면 복사하지 말고 `sources`에 그 경로를 인용한다.
URL이라면 추출한 텍스트를 저장한다. PDF라면 추출한 텍스트를 저장하고 인용할 페이지
번호를 기록한다.

어디서 왔고 언제 가져왔는지 헤더에 남긴다.

## 2. 위키가 이미 무엇을 알고 있는지 확인한다

이 단계를 건너뛰면 중복 페이지를 쓰게 된다. 매번 그렇다.

```bash
# 페이지 파일 목록 — 타입 디렉터리 전체, 빈 디렉터리에도 조용하다
PAGES=$(find wiki -mindepth 2 -maxdepth 2 -name '*.md' -not -path '*/graph/*')
grep -ri '<핵심 용어>' wiki/ --include='*.md' -l
grep -l 'raw/<관련 소스 slug>' $PAGES    # 같은 소스를 쓰는 페이지
```

`wiki/index.md`를 읽고, 인접해 보이는 페이지들을 읽는다. 두 번째 grep이 중요하다 —
같은 소스를 인용하는 기존 페이지는 이 소스와 주제가 겹칠 가능성이 가장 높은 페이지다.

## 3. 분석 (쓰기 전)

소스를 완전히 읽고, 쓰기 전에 아래를 목록으로 만든다. 실제로 적어라 — 머릿속에
두면 4단계에서 흔들린다.

- **엔티티** — 등장하는 사람·조직·시스템·제품
- **개념** — 정의되거나 설명되는 아이디어·기법
- **주장** — 소스가 사실로 내세우는 것, 각각의 근거 강도와 함께
- **소스가 밝힌 한계** — 논문·글이 스스로 인정한 것
- **기존 페이지와의 모순** — 2단계에서 읽은 페이지와 어긋나는 지점

그다음 각 항목을 기존 위키와 대조해 네 가지 중 하나로 판정한다.

- **신규 페이지** — 위키에 그 개념을 담을 곳이 없다.
- **확장** — 페이지가 이미 있다. 주장과 인용을 그 페이지에 추가한다.
- **모순** — 페이지가 반대되는 주장을 한다. 양쪽 입장을 각자의 소스와 함께 서술하도록
  페이지를 편집하고, 어느 쪽이 더 잘 뒷받침되는지와 그 이유를 밝힌다. 조용히
  덮어쓰지 말고, 충돌을 언급하지 않고 넘기지도 말 것.
- **생략** — 이미 다뤄졌거나, `purpose.md`의 범위 밖이거나, 나중에 읽을 가치가 없을
  만큼 부수적이다.

대부분의 소스는 예상보다 적은 페이지를 낳는다. 30페이지 논문에서 신규 페이지 두 개와
확장 네 건이 나오는 일이 흔하다. 대신 얇은 페이지 여러 개를 쓰는 것이 흔한 실패다 —
인덱스를 부풀리고, 정작 중요한 두 개를 묻는다.

범위 밖 주제가 반복해서 나오면 `purpose.md` 갱신을 제안한다. 조용히 범위를 넓히지 말 것.

## 4. 작성

`page-format.md`를 따른다.

**소스 페이지를 먼저 쓴다.** `type: source`로 하나. 이것이 "이 소스가 무엇을
주장했나"에 답하는 유일한 곳이고, 나머지 페이지들의 인용 대상이 된다. 3단계 분석
목록이 그대로 이 페이지의 재료다.

그다음 `concept`·`entity` 페이지를 쓰거나 확장하고, 소스 페이지의 `## 여기서 나온
페이지` 목록에 추가한다.

소스를 전부 읽으면 메인 컨텍스트가 좁아질 만큼 긴 경우에는 `wiki-scribe` 에이전트에
위임한다 — `raw/` 경로, 인접한 기존 페이지 목록, 3단계에서 결정한 페이지 집합을
넘긴다.

## 5. 마무리

아래 둘을 같은 작업 안에서 처리한다.

- **`wiki/index.md`** — 신규 페이지당 한 줄. diff를 읽기 좋게 유지하려면 카테고리 안
  에서 알파벳 순으로 둔다.
- **`wiki/log.md`** — 날짜, 소스, 생성한 페이지, 수정한 페이지를 append한다. 1년 뒤에
  오래된 내용을 진단할 수 있게 하는 감사 기록이다.

`wiki/graph/`가 있으면 재컴파일한다. 낡은 그래프는 없는 것보다 나쁘다.

```bash
python3 "<skill>/scripts/wiki_graph.py"
```

근거 없는 관계가 있으면 스크립트가 problem으로 알려준다 — 그것까지 정리하고 마친다.

그다음 사용자에게 보고한다: 생성한 페이지, 확장한 페이지, 발견한 모순, 생략한 것과 그
이유. 모순은 반드시 명시적으로 말한다 — 한눈에 보이지 않는 부분이면서 가장 중요할
가능성이 높은 부분이다.
